# V0.3 - Arquitectura Garmin Connect directa

Este documento fija la variante ambiciosa de `V0.3`: adquisicion directa desde Garmin Connect manteniendo capas internas limpias.

## 1. Decision de arquitectura

Garmin Connect entra como capa de adquisicion, no como contrato interno del sistema.

Eso significa:

1. el adaptador Garmin puede cambiar,
2. el pipeline interno no debe depender de nombres nativos de Garmin,
3. staging, deduplicacion y carga final siguen siendo propios del sistema,
4. y la trazabilidad debe registrar tanto el fetch externo como la carga relacional.

## 2. Capas resultantes

### Capa 1. Garmin Connect Adapter

Responsabilidades:
- autenticacion o reutilizacion de sesion,
- consulta de actividades por rango,
- consulta de metricas diarias por rango,
- captura de payload bruto,
- y transformacion a un contrato normalizado interno.

No debe:
- escribir directamente en `exec_activities`,
- deduplicar en tablas finales,
- ni decidir logica deportiva.

### Capa 2. Normalized Import Contract

Contrato interno minimo:
- `NormalizedActivity`
- `NormalizedDailyMetric`
- `ImportFetchMetadata`

Objetivo:
- aislar al sistema del formato o endpoint real de Garmin.

### Capa 3. Staging

Responsabilidades:
- conservar filas normalizadas por `import_job_id`,
- marcar validacion,
- explicar filas descartadas,
- y permitir reintentos o auditoria.

### Capa 4. Deduplicacion y carga

Responsabilidades:
- detectar identidades ya presentes,
- registrar insertadas, actualizadas, deduplicadas y fallidas,
- poblar `exec_activities` y `exec_daily_metrics`.

### Capa 5. API o CLI

Responsabilidades:
- exponer `preview` y `apply`,
- lanzar import jobs,
- devolver resumen y estado.

## 3. Superficies tecnicas minimas a crear

### En backend

1. `app/imports/garmin_connect.py`
2. `app/imports/contracts.py`
3. `app/imports/pipeline.py`
4. `app/imports/storage.py`

### En base de datos

1. staging de actividades Garmin
2. staging de metricas Garmin
3. uso real de `meta_import_jobs`

### En API

1. `POST /api/imports/garmin-connect/preview`
2. `POST /api/imports/garmin-connect/run`
3. `GET /api/import-jobs`
4. `GET /api/import-jobs/{import_job_id}`

### En CLI

1. `python -m app.imports.garmin_connect --season <ano> --from <fecha> --to <fecha> --dry-run`
2. `python -m app.imports.garmin_connect --season <ano> --from <fecha> --to <fecha> --apply`

## 4. Ruta de implementacion recomendada

### Paso 1
- cerrar el contrato interno normalizado.

### Paso 2
- crear staging y storage.

### Paso 3
- añadir el adaptador Garmin como proveedor de datos normalizados.

### Paso 4
- conectar preview y apply.

### Paso 5
- validar repetibilidad y deduplicacion sobre una semana real.

## 5. Riesgo principal

El mayor riesgo no es el pipeline interno, sino la capa de adquisicion Garmin:
- login,
- sesion,
- endpoints no estables,
- y disponibilidad de metadatos.

Por eso la regla de gobierno es:

> si el adaptador Garmin cambia o falla, el contrato interno y el pipeline de staging no deben redisenarse.

## 6. Resultado esperado

Si esta arquitectura se respeta, `V0.3` ambiciosa sigue siendo controlable:
- mas rica que `TCX`,
- mas util que una importacion puramente manual,
- y todavia auditable.

Estado actual:
- implementada con artefactos TCX locales por actividad en `<temporada>/Datos/Importaciones/Garmin/Actividades/<fecha>/<activity_id>.tcx`,
- y validada en API y CLI sobre un lote real corto.
