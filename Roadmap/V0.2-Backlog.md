# V0.2 - Backlog ejecutable

Este documento desglosa `V0.2` en tareas concretas y verificables.

## 1. Objetivo operativo

Cerrar un flujo minimo real en el que:
- la planificacion de B1 vive en SQLite,
- se puede registrar ejecucion manual minima,
- se puede comparar plan vs realidad,
- y se puede inspeccionar visualmente el contenido de la base.

## 2. Alcance cerrado de V0.2

Incluido:
- planificacion de 2026 cargada en SQLite,
- foco operativo sobre B1,
- registro manual minimo de ejecucion,
- enlace basico entre sesion planificada y ejecucion,
- revision semanal manual asistida,
- GUI minima de solo lectura.

Excluido:
- importacion Garmin automatizada,
- analisis avanzado,
- ajuste automatico del plan,
- GUI completa de uso diario,
- sincronizacion automatica markdown <-> SQLite.

## 3. Backlog por bloques

### Bloque A. Datos y modelo

#### A1. Validar la semilla 2026
- Descripcion: comprobar que `Sistema/Seeds/2026.sql` representa correctamente el estado actual del plan 2026.
- Salida esperada: lista de entidades semilladas validada.
- Criterio de cierre: el contenido de B1 en la base coincide con las vistas humanas actuales.

#### A2. Definir el flujo minimo de ejecucion manual
- Descripcion: decidir que campos minimos se registran para una semana real sin Garmin.
- Salida esperada: especificacion minima para `exec_activities`, `exec_daily_metrics`, `link_plan_execution` y `review_daily_reviews`.
- Criterio de cierre: existe un flujo manual corto y no ambiguo.

#### A3. Preparar datos de ejemplo para una semana real
- Descripcion: cargar un ejemplo de semana ejecutada para B1.
- Salida esperada: al menos una semana de ejemplo manual en la base.
- Criterio de cierre: la comparacion plan vs realidad puede probarse con datos reales o simulados de forma realista.

### Bloque B. Consultas y revision

#### B1. Crear consultas base de planificacion
- Descripcion: preparar consultas o vistas simples para temporada, bloques, semanas y sesiones.
- Salida esperada: consultas reutilizables para la GUI minima.
- Criterio de cierre: la GUI puede leer sin logica duplicada.

#### B2. Crear consulta basica plan vs realidad
- Descripcion: mostrar sesiones planificadas junto a ejecucion enlazada y estado de cumplimiento.
- Salida esperada: vista o consulta de comparacion semanal.
- Criterio de cierre: se puede revisar una semana concreta de B1 de extremo a extremo.

#### B3. Definir formato de revision semanal manual asistida
- Descripcion: decidir el contenido minimo de una revision semanal para V0.2.
- Salida esperada: plantilla o estructura de salida con cumplimiento, desvio y decision.
- Criterio de cierre: la revision de una semana puede completarse siempre con el mismo esquema.

### Bloque C. GUI minima de lectura

#### C1. Definir pantallas del MVP visual minimo
- Descripcion: concretar las pantallas que leeran SQLite en V0.2.
- Salida esperada: especificacion de cuatro vistas: temporadas, bloques, semanas y sesiones.
- Criterio de cierre: existe diseno funcional sin huecos para navegar de temporada a sesion.

#### C2. Elegir stack tecnico minimo
- Descripcion: fijar stack para frontend y backend minimo de la GUI de lectura.
- Salida esperada: decision documentada y justificada.
- Criterio de cierre: se puede empezar a implementar sin reabrir debate tecnologico.

#### C3. Implementar lectura minima de SQLite
- Descripcion: permitir que la GUI liste temporadas, bloques, semanas y sesiones.
- Salida esperada: GUI navegable de solo lectura.
- Criterio de cierre: el usuario puede inspeccionar B1 visualmente sin SQL ni markdown.

### Bloque D. Validacion

#### D1. Validacion tecnica
- Descripcion: comprobar que el flujo funciona sobre `Sistema/training.sqlite`.
- Salida esperada: checklist de validacion completado.
- Criterio de cierre: consultas, GUI y datos de ejemplo funcionan de forma consistente.

#### D2. Validacion de uso
- Descripcion: recorrer una semana concreta y verificar que el sistema permite entender que estaba previsto, que ocurrio y como cerrarla.
- Salida esperada: caso de uso probado sobre una semana de B1.
- Criterio de cierre: el flujo semanal minimo se considera util.

## 4. Orden recomendado dentro de V0.2

1. A1. Validar semilla 2026.
2. A2. Definir flujo manual minimo.
3. B1. Crear consultas base de planificacion.
4. C1. Definir pantallas del MVP visual minimo.
5. C2. Elegir stack tecnico minimo.
6. C3. Implementar lectura minima de SQLite.
7. A3. Preparar datos de ejemplo de una semana real.
8. B2. Crear comparacion plan vs realidad.
9. B3. Definir revision semanal manual asistida.
10. D1. Validacion tecnica.
11. D2. Validacion de uso.

## 5. Definicion de terminado de V0.2

`V0.2` se considera terminada cuando:
- B1 puede recorrerse visualmente desde la GUI,
- existe al menos una semana con ejecucion manual registrada,
- la comparacion plan vs realidad puede verse,
- y una revision semanal minima puede cerrarse con criterio repetible.
