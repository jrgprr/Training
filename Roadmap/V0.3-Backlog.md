# V0.3 - Backlog ejecutable

Este documento convierte `V0.3` en un plan de trabajo concreto, verificable y limitado.

## 0. Estado de cierre

`V0.3` ya esta cerrada en la implementacion actual con estas evidencias:
- adaptador Garmin Connect desacoplado operativo,
- staging persistente en SQLite,
- `meta_import_jobs` con trazabilidad en exito y fallo,
- endpoints API de preview, run e historial,
- CLI equivalente con `--dry-run` y `--apply`,
- deduplicacion minima reproducible por identidad Garmin,
- y validacion real de importacion sobre `2026-05-05`.

Lo que sigue en este documento debe leerse como criterio de cierre ya satisfecho o como referencia de alcance, no como trabajo pendiente abierto.

## 1. Objetivo operativo

Cerrar un flujo minimo de importacion externa en el que:
- una exportacion real ligada a Garmin entra en el sistema de forma repetible,
- queda trazabilidad de cada importacion,
- se evita duplicar actividades o metricas basicas,
- y los datos terminan cargados en `Sistema/training.sqlite` sin rehacer el proceso a mano.

## 2. Alcance cerrado de V0.3

Incluido:
- primer adaptador Garmin Connect desacoplado,
- staging explicito antes de la carga final,
- uso real de `meta_import_jobs`,
- adquisicion directa desde Garmin Connect manteniendo contrato interno estable,
- filtrado por temporada,
- deduplicacion minima reproducible,
- y carga en `exec_activities` y `exec_daily_metrics`.

Excluido:
- importacion recurrente automatica,
- analisis automatico de actividades,
- enlace automatico plan-real,
- GUI completa de importaciones,
- soporte simultaneo de todos los formatos Garmin,
- y tolerancias deportivas complejas durante la deduplicacion.

## 3. Decision de adquisicion inicial

### F1. Primer origen soportado

La primera entrada soportada para cerrar `V0.3` debe ser Garmin Connect directo a traves de un adaptador desacoplado.

El contrato oficial del sistema no debe ser la respuesta nativa de Garmin, sino un payload interno normalizado que despues entra en staging.

Motivo:
- permite capturar metadatos que pueden no estar en `TCX`,
- permite incorporar fisiologia diaria rica cuando Garmin la expone,
- evita que el modelo interno quede limitado por un formato de exportacion pobre,
- y mantiene capas limpias si Garmin se trata como adquisicion y no como contrato interno.

### F2. Contrato interno minimo a generar

1. lote normalizado de actividades
2. lote normalizado de metricas diarias
3. trazabilidad del fetch o import job

El adaptador Garmin Connect puede cambiar, pero el pipeline interno de `V0.3` solo debe depender de este contrato estable.

## 4. Modelo de datos minimo para V0.3

### A. Tablas finales ya existentes

- `exec_activities`
- `exec_daily_metrics`
- `meta_import_jobs`

### B. Staging minimo recomendado

`V0.3` debe incorporar staging explicito antes de la carga final. La opcion minima recomendable es:

1. `staging_garmin_activities`
2. `staging_garmin_daily_metrics`

Campos minimos de staging:
- `import_job_id`
- `season_id`
- `source_system`
- identidad y columnas normalizadas necesarias para carga final
- `raw_payload_path` cuando exista artefacto local
- `notes`

Objetivo del staging:
- conservar fila de origen,
- permitir validacion antes de insertar en `exec_`,
- explicar por notas y resumen por que una fila se carga o actualiza,
- y facilitar reintentos reproducibles.

### C. Uso minimo de `meta_import_jobs`

Cada importacion debe registrar como minimo:
- `season_id`
- `source_system = 'garmin'`
- `import_type = 'garminconnect'`
- `source_path`
- `rows_detected`
- `rows_loaded`
- `status`
- `notes`

Estados minimos recomendados:
- `running`
- `completed`
- `failed`

## 5. Reglas minimas de deduplicacion

### D1. Actividades

Regla principal:
- usar `source_system + external_activity_id` como identidad primaria cuando exista.

Regla de respaldo si falta `external_activity_id`:
- considerar duplicada una fila si coincide exactamente en:
  - `season_id`
  - `activity_date`
  - `activity_type`
  - `duration_seconds`
  - `distance_meters`

Comportamiento minimo:
- no crear una segunda actividad si la identidad ya existe,
- dejar trazabilidad en el job de que la fila fue deduplicada,
- y no borrar nunca datos previos durante la importacion normal.

### D2. Metricas diarias

Regla principal:
- respetar la unicidad ya definida en `exec_daily_metrics`:
  - `season_id, metric_date, source_system`

Comportamiento minimo:
- hacer `upsert` controlado,
- sobrescribir solo dentro de la misma combinacion de identidad,
- y registrar en el job si fue insercion nueva o actualizacion.

## 6. Comandos y endpoints minimos

### E1. Comando CLI minimo aceptable para cerrar V0.3

El cierre de `V0.3` puede lograrse solo con CLI si la GUI aun no llega a importaciones.

Comando objetivo:

```bash
python -m app.imports.garmin_connect --season 2026 --from 2026-05-04 --to 2026-05-10 --dry-run
python -m app.imports.garmin_connect --season 2026 --from 2026-05-04 --to 2026-05-10 --apply
```

Capacidades minimas:
- autenticar o reutilizar sesion del adaptador,
- traer actividades y metricas diarias del rango,
- normalizar al contrato interno,
- crear `meta_import_jobs`,
- poblar staging,
- deduplicar,
- cargar en tablas finales,
- y devolver un resumen legible.

### E2. Endpoints minimos recomendados si se expone por API

1. `POST /api/imports/garmin-connect/preview`
2. `POST /api/imports/garmin-connect/run`
3. `GET /api/import-jobs`
4. `GET /api/import-jobs/{import_job_id}`

No son obligatorios para cerrar `V0.3` si el flujo CLI ya es reproducible, pero si se implementan deben mapear exactamente al mismo pipeline que el CLI.

## 7. Backlog por bloques

### Bloque A. Contrato de entrada

#### A1. Fijar el contrato CSV inicial
- Descripcion: definir el contrato normalizado entre el adaptador Garmin Connect y el pipeline interno.
- Salida esperada: especificacion de campos obligatorios y opcionales para actividades y metricas diarias.
- Criterio de cierre: el pipeline puede validar el schema sin ambiguedad aunque cambie el origen Garmin.

#### A2. Preparar acceso real de prueba
- Descripcion: fijar la estrategia minima de autenticacion o sesion para un fetch real de prueba.
- Salida esperada: una ruta controlada para consultar una semana real desde Garmin Connect.
- Criterio de cierre: existe una semana real obtenible varias veces desde el adaptador.

### Bloque B. Pipeline

#### B1. Crear staging minimo
- Descripcion: introducir tablas o estructuras de staging previas a la carga final.
- Salida esperada: staging consultable por `import_job_id`.
- Criterio de cierre: cada fila importada deja rastro antes de tocar `exec_`.

#### B2. Implementar el adaptador Garmin Connect inicial
- Descripcion: consultar Garmin Connect, recuperar actividades y metricas diarias del rango y entregarlas al contrato interno.
- Salida esperada: comando reproducible de preview y apply.
- Criterio de cierre: el pipeline se ejecuta de inicio a fin sin pasos manuales intermedios fuera del propio adaptador.

#### B3. Aplicar deduplicacion minima
- Descripcion: evitar duplicados en actividades y metricas diarias.
- Salida esperada: reglas deterministas y comprobables.
- Criterio de cierre: ejecutar dos veces el mismo lote no duplica datos finales.

#### B4. Cargar tablas finales
- Descripcion: mover datos validados a `exec_activities` y `exec_daily_metrics`.
- Salida esperada: insercion final correcta filtrada por temporada.
- Criterio de cierre: los datos importados aparecen en SQLite con identidad coherente.

### Bloque C. Trazabilidad

#### C1. Registrar import jobs
- Descripcion: usar `meta_import_jobs` en cada importacion.
- Salida esperada: una fila por ejecucion del pipeline.
- Criterio de cierre: se sabe que se intento importar, desde donde y con que resultado.

#### C2. Resumen de importacion
- Descripcion: devolver un resumen final con detectadas, cargadas, deduplicadas y fallidas.
- Salida esperada: salida legible por CLI o API.
- Criterio de cierre: el usuario puede auditar el resultado sin leer tablas manualmente.

Implementacion actual:
- actividades y metricas informan `inserted/updated`,
- el historial conserva `breakdown` por job,
- y los fallos de fetch o persistencia quedan anotados como `failed`.

### Bloque D. Validacion

#### D1. Validacion tecnica
- Descripcion: ejecutar preview y apply sobre un lote real o equivalente.
- Salida esperada: comprobacion de staging, jobs y tablas finales.
- Criterio de cierre: el pipeline es repetible y no duplica.

#### D2. Validacion de uso
- Descripcion: importar una semana real desde Garmin Connect sin rehacer a mano el registro manual.
- Salida esperada: semana disponible en SQLite lista para fases posteriores.
- Criterio de cierre: el usuario puede traer datos reales con una secuencia corta y repetible.

## 8. Orden recomendado dentro de V0.3

1. A1. Fijar el contrato interno inicial.
2. A2. Preparar acceso real de prueba.
3. B1. Crear staging minimo.
4. C1. Registrar import jobs.
5. B2. Implementar el adaptador Garmin Connect inicial.
6. B3. Aplicar deduplicacion minima.
7. B4. Cargar tablas finales.
8. C2. Resumen de importacion.
9. D1. Validacion tecnica.
10. D2. Validacion de uso.

## 9. Definicion de terminado de V0.3

`V0.3` se considera terminada cuando:
- existe una ruta directa y repetible de adquisicion desde Garmin Connect,
- el pipeline puede ejecutarse de forma repetible,
- cada importacion deja trazabilidad en `meta_import_jobs`,
- no se duplican actividades ni metricas basicas al repetir el mismo lote,
- y una semana real puede incorporarse a `Sistema/training.sqlite` sin rehacer el registro a mano.

- cumplido.
